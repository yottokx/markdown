# MarkNotes追加に向けたプロジェクト配置方針

決定日: 2026-09-12

この文書は両アプリを独立して保守するための配置方針です。2026-09-12に配置整理とMarkNotes開発ベースの作成を実施しました。実施内容と検証結果は[整理作業の記録](project-reorganization.md)を参照してください。スクラップブック固有機能と配布EXEのビルドは今回の対象外です。

## 1. 採用する構成

**現在のGitリポジトリの中に、既存MarkdownエディタとMarkNotesの独立したuvプロジェクトを並べる。両アプリの開発・修正・テスト・PyInstallerビルド・配布は、それぞれの判断とタイミングで行う。**

- リポジトリのルートは当面 `C:\Python\envs\markdown` のままとする。
- 既存エディタは `apps/md-editor/`、新アプリは `apps/marknotes/` に置く。
- 各アプリが `pyproject.toml`、`uv.lock`、`.python-version`、ソース、リソース、テスト、配布設定を所有する。
- 仮想環境と依存関係の更新もアプリ単位にする。ルートはuv workspaceにせず、ルート共通のロックファイルは作らない。
- Gitの履歴は1つにまとめる。アプリごとに別の `.git` を作らない。
- 既存エディタの追加テスト・不具合修正・配布ビルドの完了を、MarkNotesの着手・開発継続の条件にしない。エディタ側の修正・ビルドもMarkNotesの進捗を待たない。

既存エディタは仕様が概ね固まっている一方、実際のテストはまだ十分ではなく、今後も検証と修正を続けるアプリとして扱う。どちらのアプリも変更される前提で、一方のコード・依存関係の変更が他方へ自動的に波及しない構成にする。一部のコードの重複は、独立して保守するために許容する。

│   │   ├── src/md_editor/
│   │   │   └── resources/          # アイコン・CSS・JS・vendor・ライセンス

MarkNotesにも専用の `.venv/` と検証用 `artifacts/` を置く。`build/` と `dist/` はそのアプリのビルド時に生成する。空ディレクトリや未使用の実装モジュールを先に大量作成しない。

現在のルートにある `src/`、`tests/`、`packaging/`、`tools/`、`examples/`、アプリの設定ファイル・ロックファイルと既存文書は、まとまりを保って `apps/md-editor/` へ移す。既存の `artifacts/` もエディタ側に帰属させる。ルートのREADMEは両アプリへの入口として新しく用意する。

既存文書の相対リンクは可能な限り維持し、移動前の絶対パスで書かれたリンクは移動時に更新する。開発記録は既存エディタ側を正本とし、MarkNotesの記録と混在させない。

## 3. アプリの独立性

| 項目 | 既存Markdownエディタ | MarkNotes |
| --- | --- | --- |
| 目的 | 任意の `.md` ファイルを開いて編集 | スクラップブックとしてノートを扱う |
| Pythonパッケージ | `md_editor` を維持 | `marknotes` |
| 起動コマンド | `md-editor` を維持 | `marknotes` |
| 配布EXE | `md-editor.exe` を維持 | `marknotes.exe` |
| 依存関係 | 既存の定義・lockを引き継ぎ、独立して更新 | 独立した定義・lockで管理 |
| 設定・アプリID | 現在の識別子を維持 | MarkNotes固有の識別子を使用 |
| バージョン・配布時期 | エディタ単独で決定 | MarkNotes単独で決定 |

既存エディタは現在 `QSettings("MdEditor", "Markdown Editor")` を使用し、画像操作の復旧データを `QStandardPaths.AppLocalDataLocation` 以下に保存している。MarkNotesではQSettings、QApplicationのアプリ名、Windows AppUserModelIDを分け、設定・復旧データ・ウィンドウ識別が衝突しないようにする。

ノート本文・添付画像などの利用者データはソースや `dist/` 内に保存しない。MarkNotesの保存先・ファイル形式・DB採用の有無は、ノート管理の要件を決める段階で設計する。既存エディタの `img/MD名_連番` 方式を、そのままMarkNotesの保存仕様として固定しない。

各アプリのディレクトリから起動・テスト・ビルドできる状態を基本にする。既存エディタは `apps/md-editor/` に移動してから、従来どおり `uv run md-editor` で起動する。

独立性の確認条件は次のとおりとする。

- 他方のアプリのディレクトリ・仮想環境・ビルド成果物がなくても、自分のプロジェクトとlockから環境構築・テスト・ビルドができる。
- PyInstallerの入口・参照パス・同梱リソース・出力先はアプリ内で完結させ、兄弟アプリのコードやファイルを参照しない。
- 一方の修正・依存関係更新・リリースに、他方の変更・全テスト成功・再ビルドを必須としない。変更したアプリに必要な検証は、そのアプリ側で行う。
- バージョン、配布物、検証記録をアプリ別に管理する。リリース用タグを設ける場合も `md-editor/v...` と `marknotes/v...` のように区別する。

同じGitリポジトリでも、この独立性は維持できる。異なるブランチで同時に作業する場合は別worktreeを使い、作業途中の変更を分離する。両アプリを一括リリースする運用は前提にしない。

## 4. 既存コードの利用と共通化

初期MarkNotesは、既存実装のうち必要な編集・プレビュー処理と、その依存コード・リソース・関連テストをコピーして出発する。コピー元のコミットと対象範囲をMarkNotesの文書に記録し、パッケージ参照をMarkNotes側へ変更する。

- 両アプリ間の相互importやローカルパス依存を作らない。MarkNotesから `md_editor.app.MainWindow` や既存アプリ本体を直接importしない。
- 既存エディタの全体ウィンドウを、共通の基底クラスとして継承しない。
- 共通化を目的とした既存エディタの大規模な作り直しは、今回の整理に含めない。
- コピーしたコードの修正は各アプリで管理する。両方に関係する不具合修正は必要性を確認して個別に反映・検証する。他方への反映は元のアプリの修正・配布を完了させる条件にしない。
- 同梱するKaTeX・Mermaid等のvendorリソースは必要なライセンス文書を含めて引き継ぐ。

現在のMainWindowは、ファイル操作・画像操作・表示切り替え・出力等を統合している。ノート管理のUIと任意ファイルの編集UIは責務が異なるため、最初から同じウィンドウ構造へ統一しない。

共通化は必須の到達点にしない。将来、Markdown変換や編集・プレビュー部品などで共通化の利点が確認できた場合だけ検討する。採用する場合は、バージョンを固定できる独立パッケージとし、各アプリが更新の取り込み時期を選べるようにする。同じ作業中のソースディレクトリを両アプリから直接参照する方式は採らない。共通パッケージもアプリに依存させない。

## 5. 環境・生成物・参考資料

- 現在の `.venv/` はプロジェクト配下にあり、プロジェクトルート自体は仮想環境ではない。整理時には `.venv/` を移動せず、移動先で既存lockに従って再作成する。
- `__pycache__/`、`.pytest_cache/`、`.ruff_cache/`、`.uv-cache/` とビルド中間生成物は新構成へ引き継ぐ対象にしない。必要に応じて再生成する。
- 現在の `dist/` は段階1〜2の旧版。保存する旧配布物は、エディタの `artifacts/legacy-dist/` 等に旧版であることを明記して保管し、新しい `dist/` と区別する。
- 検証用の画像・HTML・PDFは `artifacts/` に保持する。コード整理を理由に既存の検証記録を削除しない。
- ルートの `.gitignore` で両アプリの仮想環境・キャッシュ・ビルド出力・検証成果物を除外する。実行に必要なresourcesとライセンス、テスト用fixtureはGit管理対象にする。
- `参考/prompt_editor_demo/` は `references/prompt_editor_demo/` として開発用資料に分離する。アプリのimport先・配布物には含めない。

## 6. 実際に整理する際の順序

1. **現状を復元できる基準を保存する。** 2026-09-12の確認時点でGitにはコミットがなく、ソース等はすべて未追跡だった。管理対象を確認して現状を初期コミットとして保存し、Git管理外の検証成果物・旧配布物も別途保全する。
2. 現在の配置で既存テストと静的チェックを実行し、基準結果を記録する。SESSION_SUMMARYにある非表示プレビューの位置復元テストの断続的失敗は、既知事項として切り分ける。
3. 既存アプリ一式を `apps/md-editor/` へ移す。この作業では配置・起動案内・必要なパスだけを調整し、機能変更を混ぜない。`md_editor` というパッケージ名を維持する。
4. 既存lockから環境を再作成する。spec・tools・テストのアプリルート基準のパスと同梱リソースを確認し、移動前後のテスト・静的チェック・起動結果を比較する。配置変更で生じた問題を修正し、既存の検証不足や不具合はエディタ側の継続課題として記録する。
5. 整理済みの基準を保存し、MarkNotesの独立プロジェクトを作成する。コピー元の状態と既知事項を記録し、既存実装の取り込みとMarkNotes固有機能の開発を進める。エディタ側の追加テスト・修正・PyInstallerビルドの完了は待たない。

整理後は、次の2つの作業を独立して進める。

- **既存エディタ:** 実操作での追加テスト、不具合修正、必要な時点でのPyInstallerビルド・配布検証を行う。段階7のビルドもこの作業に属する。配布時にはEXE起動、日本語パスを含むファイル引数、同梱リソース、オフライン描画・出力等を確認する。
- **MarkNotes:** ノート管理の要件整理、実装、テスト、ビルドを独自の進捗で行う。コピーした機能の検証と修正もMarkNotes側で行う。

エディタの初回配布ビルドを開発終了の区切りとはせず、その後も必要に応じて修正・再ビルドする。

上記の整理手順を実施し、基準保存・配置変更・環境再作成・検証を行った。詳細は[整理作業の記録](project-reorganization.md)に記載する。配布EXEのビルドは各アプリの独立した作業として残っている。
