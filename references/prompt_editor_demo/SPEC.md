# Prompt Editor Demo 仕様案

- ステータス: Draft
- 作成日: 2026-08-23
- 対象: `prompt_editor_demo/` として開発する独立試作アプリ

短い実装対象は[MVP仕様](MVP_SPEC.md)を参照する。この文書は将来案と未決事項を含む詳細版とする。

## 1. 目的

AIエージェントアプリへ入力するプロンプトを、素早く記述・補完するためのコンパクトなMarkdownソースエディタを試作する。

特に次を実際の操作感から検証する。

- `?`記法による明示的なAI補完が実用的か
- リストと引用の自動インデントが自然に操作できるか
- ゴーストテキストが必要か、むしろ邪魔になるか
- Tab、Backspace、Esc、IME入力が衝突しないか
- 通常のチャットとは異なる短時間の補完処理に適したUIとAPI境界

## 2. 試作の位置付け

本試作はDesktop LLM本体へ直接組み込まず、同じリポジトリとPySide6基盤上で動作する別アプリとして作成する。

- 本体のチャット履歴、設定DB、添付、ホットキーへ影響を与えない
- 最初は独立したウィンドウとして直接起動する
- 操作仕様が固まった後、再利用可能なロジックとUIだけを本体へ移植する
- 本体統合時に、設定済みプレフィックスと`W`を組み合わせたホットキーを追加する想定
- 本体統合およびF13+Wは、試作段階の対象外とする

## 3. 決定済みの基本方針

- 基本UIはコンパクトなテキストエディタとする
- Markdownをレンダリングせず、ソースのまま編集する
- Markdownシンタックスハイライトに対応する
- Tabキーでタブ文字は挿入しない
- リストと引用で自動インデントを行う
- AIモードをワンタッチでON/OFFできるようにする
- AIによる明示的な補完には`?`記法を使用する
- キャレットが`?`ブロック内にある状態でTabを押すと、そのブロックを補完する
- 選択範囲に複数の`?`ブロックがある状態でTabを押すと、範囲内の対象をすべて補完する
- `?`補完は、インデントやその他のAI補完より優先する
- リスト補完は、末尾に半角`...`がある場合だけ複数項目を生成する
- ゴーストテキストの採否は、試作を操作してから決定する

## 4. 初期試作に含めないもの

次は操作検証後に判断する。

- 本体への統合
- F13+Wのグローバルホットキー
- アクティブアプリのキャレット位置取得
- 元アプリへの自動貼り付け
- ドラフトの永続化
- モデルサーバーの起動、停止、常駐管理
- 入力停止後の自動AI補完
- レビュー、添削、差分適用
- 複数の実APIに対する互換性検証

## 5. `?`記法

### 5.1 共通規則

- 半角の`?`だけを制御記号として扱う
- 全角の`？`は通常文字として扱う
- 有効な構文へ完全に一致したものだけを`?`ブロックとして扱う
- 単独の`?`や不完全な記法は、Tabの他の動作を妨げない
- 解析の優先順位は「リスト補完」「段落生成」「文中補完」とする
- 認識済みの記法はシンタックスハイライトで明示する

次の範囲にある`?`は補完記法として扱わない方針を暫定とする。

- Markdownのフェンスコードブロック内
- Markdownのインラインコード内
- URL途中のクエリ文字としての`?`
- `\?`のようにバックスラッシュでエスケープされた`?`

### 5.2 文中補完

記法:

```text
私は ?人名 です。
```

規則:

- `?`とヒントは空白を入れずに連結する
- ブロックの直前には半角スペースが必要
- ブロックの直後には半角スペース、改行、または文書末尾が必要
- ヒントには空白を含めない
- 補完結果は改行を含まない短い文字列とする
- 記法の区切りに使用した前後の半角スペースも置換時に削除する

例:

```text
入力: 私は ?人名 です。
結果: 私は山田太郎です。
```

空白を含むヒントが必要になった場合は、将来の拡張候補として`?{架空の日本人のフルネーム}`のような記法を検討する。初期試作には含めない。

### 5.3 段落生成

記法:

```text
? 注意点を説明する
```

規則:

- 行の最初の非空白文字が`?`である
- `?`とヒントの間には半角スペースを入れる
- ヒントは行末までとし、空白を含められる
- `?`または`? `だけの行は無効とする
- ディレクティブ行全体を生成結果へ置換する
- 行頭のインデントは維持する
- 生成結果は原則として1段落とする
- 見出しやリストは、ヒントで明示的に要求された場合だけ生成する

例:

```text
入力:
? APIキーを扱う際の注意点を説明する

結果:
APIキーは設定ファイルやログへ平文で保存せず、OSの資格情報ストアなどを利用して管理する。
```

### 5.4 リスト項目の単一補完

記法:

```text
- ?注意点
```

規則:

- Markdownリスト項目の本文先頭に`?ヒント`を置く
- `?`とヒントは空白を入れずに連結する
- ヒントには行末までの文字列を使用できる
- 末尾に半角`...`がない場合は、現在のリスト項目を1件だけ補完する
- モデルは項目本文だけを返し、リストマーカーとインデントはエディタが付与する

例:

```text
入力: - ?APIキーの注意点
結果: - APIキーをログへ出力しない
```

### 5.5 リスト項目の複数生成

記法:

```text
- ?注意点を3つ程度...
```

規則:

- ヒント末尾の半角ピリオド3個`...`を複数生成の制御記号として扱う
- `...`の後ろには空白または改行だけを許可する
- 全角の三点リーダー`…`は通常文字として扱う
- 行中にある`...`や、末尾以外に文字が続く`...`は制御記号として扱わない
- 制御記号の`...`はモデルへそのまま渡さない
- 生成された各項目へ、元のリストマーカーとインデントを付与する
- ヒントに件数指定がある場合はその指定を優先する
- 件数指定がない場合の既定値は、暫定的に3件とする
- 異常に多い出力を防ぐ上限は、暫定的に10件とする
- 各項目は原則として1段落とし、ネストしたリストは明示的に要求された場合だけ許可する

例:

```text
入力:
  - ?セキュリティ上の注意点を3つ...

結果:
  - 入力値を検証する
  - 秘密情報をログへ出力しない
  - 権限を必要最小限にする
```

初期試作で認識するリストマーカーは`- `だけとする案を暫定とする。`* `、`+ `、番号付きリスト、タスクリストは後から拡張可能な構造にする。

## 6. `?`ブロックの範囲

選択範囲がない場合:

- 文中補完は、`?`からヒント末尾までをブロックとする
- 段落生成は、ディレクティブ行全体をブロックとする
- リスト補完は、ディレクティブを含むリスト行全体をブロックとする
- キャレットが対象ブロック内にあるとき、Tabでそのブロックを補完する

選択範囲がある場合:

- `?`文字が選択範囲に含まれる有効なブロックを対象とする
- ブロック全体を厳密に選択する必要はない
- 対象が複数種類混在していても、一回の操作ですべて補完する
- 無効な`?`や通常の疑問符は対象に含めない

## 7. Tabの優先順位

Tabの動作は、暫定的に次の順序で判定する。

1. IME変換中ならIMEへ渡す
2. 選択範囲内に有効な`?`ブロックがあれば、範囲内の全ブロックを補完する
3. キャレットが有効な`?`ブロック内にあれば、そのブロックを補完する
4. リストまたは引用のインデント操作が可能なら、インデントする
5. AIモードONかつ行末補完の条件を満たす場合は、行末までを補完する
6. いずれにも該当しない場合は何もせず、タブ文字も挿入しない

有効な`?`ブロックが補完対象にある限り、同じTab操作でインデントや通常のAI補完へフォールスルーしない。

Shift+Tabは`?`補完を開始せず、インデントを1段階浅くする操作へ予約する案を暫定とする。

### 7.1 行末補完

選択範囲と有効な`?`補完対象がなく、キャレットが改行または文書末尾の直前にある場合は、直前の文字がMarkdown制御文字でないときだけ行末補完を実行する。空行、Markdownプリフィックスだけの行、コード内、同じ行に未補完の`?`がある場合は実行しない。応答は改行を含めず、既存の行を繰り返さずにキャレット位置へ追記する。

## 8. AIモード

AIモードの意味は未決だが、初期試作では次を暫定仕様とする。

- AIモードOFFではAPIリクエストを一切送らない
- AIモードOFF中に`?`ブロック上でTabを押した場合、他の補完へフォールスルーしない
- その場合は`AIがOFFです`と短時間表示する
- AIモードをONからOFFへ切り替えた場合、進行中のリクエストをキャンセルする
- 疑似AIと、Desktop LLMの既存モデルプロファイルを使う実APIを切り替えられる

明示的な`?`補完だけをAIモードOFFでも許可したい場合は、トグルの名称と意味を「AIモード」ではなく「自動補完」に変更する必要がある。

## 9. 補完の実行と置換

### 9.1 処理中

- 対象ブロックを処理中表示にする
- 複数対象の場合は`4か所を補完中`のように件数を表示する
- 同一処理中のTab連打で重複リクエストを開始しない
- Escで進行中の補完をキャンセルする

### 9.2 古い結果の破棄

リクエスト開始時点の文書リビジョン、対象範囲、対象文字列を保持する。

応答受信時に次のいずれかが変化していた場合は、結果を文書へ適用しない。

- 文書の内容
- 対象ブロックの位置または文字列
- 選択範囲
- AIモード
- 現在の補完世代ID

### 9.3 一括適用

- 複数ブロックの補完は、可能なら1回のAIリクエストで行う
- 応答は対象IDと補完種別を含む構造化データとして受け取る
- すべての応答を検証してから文書へ適用する
- 一部欠落、形式不正、件数上限超過の場合は、原則として全文書を変更しない
- すべての置換を1つの編集トランザクションにまとめる
- Ctrl+Z一回ですべての置換を元に戻せるようにする

## 10. シンタックスハイライト

Markdownの基本要素に加え、`?`記法を表示上区別する。

- 見出し
- リストと引用のプリフィックス
- 強調、取り消し線
- インラインコード
- フェンスコードブロック
- リンク
- 水平線
- 有効な`?`制御記号
- `?`ヒント部分
- 複数生成を示す末尾`...`
- 処理中の`?`ブロック

無効な`?`記法は通常テキストとして表示し、エラー表示で入力を妨げない。

## 11. 未補完ブロックの管理

- 文書内の有効な未補完ブロック数を小さく表示する
- 表示例は`? 3`とする
- 将来はクリックまたはショートカットで、次または前の未補完ブロックへ移動できるようにする
- 文書をコピーまたは確定するときに未補完ブロックが残っている場合の扱いは未決とする
- 初期試作では確認ダイアログを出さず、未補完数の表示だけで検証する

## 12. ゴーストテキストの検証

初期状態はゴーストテキストなしとし、`?`補完は応答完了後に直接置換する。

後から次を独立してON/OFFできる試験機能として追加できる構造にする。

- リスト・引用プリフィックスのゴースト表示
- AI一行補完のゴースト表示
- AI複数行補完のプレビュー表示

ゴースト候補は確定済み文書へ挿入せず、コピー、選択、Undo、IME、Markdownハイライトへ混入させない。

## 13. 自動インデント

自動インデントの詳細は、`?`記法の操作確認と並行して試作する。

- リスト入力中にEnterを押すと、同じレベルの次項目を用意する
- 行頭がリストプリフィックスだけの場合、Tabで1段階深くする
- Shift+Tabで1段階浅くする
- Tabによってタブ文字は挿入しない
- 有効な`?`補完対象がある場合は、インデントより`?`補完を優先する
- 引用にも同等の操作体系を適用する

プリフィックスをゴースト表示するか、Enter時点で実文字として挿入するかは比較検証する。

## 14. 初期UI案

初期試作は次の最小構成とする。

- Markdownソースを編集する`QPlainTextEdit`
- AIモードON/OFFトグル
- 疑似AIの遅延を切り替える開発用コントロール
- 未補完ブロック数
- 補完中ステータス
- 新規作成またはクリア
- コピー

Markdownのレンダリングプレビュー、チャット履歴、添付、モデルプロファイル設定は置かない。

## 15. 疑似AI

UI操作とモデル品質を分離して検証するため、最初は決定論的な疑似AIを使用する。

最低限、次の応答を再現できるようにする。

- 文中の短い補完
- 1段落の生成
- リスト項目1件の生成
- リスト項目複数件の生成
- 0.3秒、1.5秒、3秒程度の疑似遅延
- キャンセル後に遅れて到着する応答
- 構造不正な応答
- 一部の対象が欠落した複数補完応答

## 16. 構成案

```text
prompt_editor_demo/
├─ SPEC.md
├─ __init__.py
├─ main.py
├─ editor.py
├─ markdown_highlighter.py
├─ directives.py
├─ indentation.py
├─ completion.py
├─ mock_provider.py
└─ tests/
   ├─ test_directives.py
   ├─ test_indentation.py
   └─ test_completion.py
```

責務:

- `directives.py`: Qtに依存しない`?`記法の解析と対象範囲判定
- `indentation.py`: Qtに依存しないリスト・引用の状態遷移
- `completion.py`: 補完要求、キャンセル、世代管理、応答検証
- `mock_provider.py`: 疑似AI応答
- `markdown_highlighter.py`: Markdownと`?`記法の表示
- `editor.py`: キー操作、IME、描画、Undoトランザクション
- `main.py`: 独立試作アプリの起動

本体へ移植する際は、Qt非依存の解析ロジックと補完境界を優先して再利用する。

## 17. テスト観点

### 17.1 `?`記法

- 文中補完の前後境界
- 文末の文中補完
- 空白を含む無効な文中ヒント
- 行頭とインデント後の段落生成
- `?`だけの無効な段落生成
- 単一リスト補完
- 末尾`...`による複数リスト生成
- 行中の`...`が複数生成にならないこと
- 全角`…`が通常文字になること
- コードブロック、インラインコード、URL、エスケープ内の除外
- 複数種類のブロックが混在する選択範囲

### 17.2 キー操作

- Tabの優先順位
- Shift+Tabのインデント
- Tab文字が挿入されないこと
- IME未確定中に補完しないこと
- Escキャンセル
- Tab連打による重複要求の防止
- AIモードOFF時の動作

### 17.3 非同期処理

- 入力後に届いた古い応答を破棄すること
- 選択変更後に届いた応答を破棄すること
- キャンセル後に届いた応答を破棄すること
- 複数置換が一回のUndoで戻ること
- 不完全な複数応答で文書を変更しないこと

## 18. 初期試作の完了条件

- 独立アプリとして起動できる
- Markdownソースを通常どおり入力・選択・コピー・Undoできる
- 3種類の`?`記法をハイライトできる
- `...`の有無によって単一／複数リスト補完を切り替えられる
- キャレット位置と選択範囲に応じてTabの補完対象を決定できる
- 疑似AIを使って補完、キャンセル、古い応答の破棄を検証できる
- 複数補完を一回のUndoで戻せる
- コード内や不完全な`?`が誤作動しない
- 未補完ブロック数を確認できる
- ゴーストなしの操作感を実際のプロンプト作成で評価できる
